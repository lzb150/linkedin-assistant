# Design: Dashboard v2 — durable state, pipeline tracking, find & freshness

**Date:** 2026-06-20
**Status:** approved for implementation
**Primary files:** `state-server.mjs` (new), `dashboard.mjs`, `followup.mjs` (new),
`lib/job-state.mjs` (new), `lib/followup.mjs` (new), `Jobs.app` launcher,
`com.eugene.jobs-followup.plist` (new)

## Goal

Turn the static, `localStorage`-only dashboard into a durable, server-backed
job-search workspace. State (Applied status, applied-date, per-job notes,
last-visit) moves to disk so it survives a browser reset and so the existing
macOS Notifier can fire follow-up reminders. Add day-to-day workflow features:
text/source/score search, and a "new since last visit" indicator.

This is a single combined spec; the implementation plan is phased (below).

## Context (current state)

- `dashboard.mjs` generates a self-contained `applications/index.html` from the
  `applications/*.md` packages, sorted by score. State lives in `localStorage`
  under `jobStatus` as `{ "<url>": "viewed" }` — a binary New/Viewed only. The
  earlier 3-state funnel and Export/Import were removed for simplicity.
- `applications/*.md` frontmatter already carries `generated` (first-built
  timestamp), `url`, `title`, `company`, `source`, `score`, `matched_skills`,
  `cover_language`, `salary`. No new discovery data is required for freshness.
- The codebase convention is: pure helpers in `lib/`, a thin shell script that
  wires them, and a `*.test.mjs` per module. Notifications must use `osascript`
  (terminal-notifier shows no banners on macOS 26).

## Decisions (locked during brainstorming)

- **State storage:** a tiny local Node server persists `job-state.json` to disk.
- **Server:** binds `127.0.0.1:7777` only; never exposed. Launch-on-dock-click
  (guarded), not an always-on launchd service.
- **Funnel:** `New → Viewed → Applied` (reintroducing Applied). No
  Interview/Offer/Rejected stages.
- **Find filters:** text + source + min-score. Language filter is YAGNI.
- **Follow-up reminders:** delivered through the existing Notifier via
  `osascript`, on a daily launchd schedule.
- **Packaging:** one combined spec, internally phased plan.

## Architecture

```
Jobs.app (dock)
  ├─ ensure state-server.mjs running (pgrep/port guard) ─┐
  └─ open http://127.0.0.1:7777/                         │
                                                          ▼
browser  ──GET /──────────►  applications/index.html  (generated by dashboard.mjs)
         ──GET /state─────►  job-state.json  (read)
         ──POST /state────►  job-state.json  (atomic read-modify-write)

followup.mjs (launchd, daily)
         ──reads──────────►  job-state.json + applications/*.md
         ──osascript──────►  macOS notification: "Follow up: <company> (applied Nd ago)"
```

### `state-server.mjs` (thin HTTP shell, zero deps, `node:http`)

Routes:
- `GET /` → serve generated `applications/index.html` (404 with a hint if it
  doesn't exist yet).
- `GET /state` → return `job-state.json` as JSON (`{}` if absent).
- `POST /state` → body `{ url, patch }`; merge `patch` into the entry for `url`,
  set `updatedAt`, write atomically. Also accepts `{ _meta: {...} }` to update
  top-level metadata (e.g. `lastVisit`).
- `GET /health` → `{ ok: true }` for the dashboard's reachability probe.

Behaviour:
- Atomic write: serialize to `job-state.json.tmp`, then `rename`. A crash
  mid-write never corrupts the live file.
- Single-process, synchronous read-modify-write per POST (no concurrency beyond
  one local browser; serialized by the event loop).
- Bind `127.0.0.1` explicitly. Refuse non-localhost (defence in depth).

Lifecycle:
- Started by the `Jobs.app` launcher / `run.sh`. Before starting, check whether
  port 7777 is already listening (or `pgrep` the server); if so, skip the start
  and just `open` the URL. Mirrors the existing duplicate-launch guards
  (`e0c156e`, `b584511`). Process stays up until logout / manual kill.

### `lib/job-state.mjs` (pure, unit-tested)

The server is a shell around these pure functions:
- `normalize(raw)` → canonical state map. Accepts the legacy `{url: "viewed"}`
  string shape and upgrades each to `{ status, updatedAt }`. Drops invalid
  statuses (outside `{viewed, applied}`; `new` is virtual and never stored).
- `merge(map, url, patch)` → new map with the entry updated and `updatedAt` set;
  returns the new map (no mutation).
- `validate(patch)` → boolean; guards status enum, ISO dates, note as string.

### `job-state.json` shape

```json
{
  "_meta": { "lastVisit": "2026-06-20T09:00:00Z" },
  "https://www.linkedin.com/jobs/view/4425183818/": {
    "status": "applied",
    "appliedAt": "2026-06-15T10:00:00Z",
    "note": "Recruiter Anna wants a take-home",
    "updatedAt": "2026-06-15T10:00:00Z"
  }
}
```

Missing job entry = status `new`. `_meta` holds dashboard-wide metadata.

## Features

### 1. Find — search + filters (client-side)

- Debounced (~150 ms) **text search** over title + company + matched skills.
- **Source** toggle chips: linkedin / dou / djinni / jooble.
- **Min-score** preset segment: `≥40` / `≥30` / `All`.
- Filters AND together with the existing status filter; header counters
  recompute on every change. No server involvement.

### 2. Freshness — "new since last visit"

- `dashboard.mjs` bakes each card's `generated` value into `data-generated`.
- `_meta.lastVisit` (server-side, durable) is read on load. Cards with
  `generated > lastVisit` get a **🆕 ribbon**; the header shows
  "🆕 N new since last visit" as a clickable filter.
- `lastVisit` is advanced to "now" via `POST /state` a few seconds after load
  (so the current view's "new" set stays stable while reading).

### 3. Tracking — Applied + applied-date

- Segmented control becomes **New · Viewed · Applied** again.
- Setting **Applied** records `appliedAt = now`; the card shows "applied Nd ago".
- Visual states: New = normal, Viewed = dimmed (`opacity: .55`), Applied = green
  left accent + check, not dimmed (per the 2026-06-07 status-tracking spec).
- Status filter regains `Applied (N)`.
- Auto-status triggers (open job link, expand cover letter) still set `viewed`
  but never downgrade an `applied` card.

### 4. Capturing context — per-card notes

- A **📝 Note** expander per card with a textarea; saves the `note` field via
  `POST /state` on blur (debounced). A 📝 indicator marks cards that have a note.

### 5. Follow-up reminders — Notifier

- `lib/followup.mjs` (pure, unit-tested): `dueReminders({ stateMap, now, thresholdDays = 7, alreadyNotified })`
  → list of `{ url, daysSince }` for jobs with `status === "applied"` whose
  `appliedAt` is older than `thresholdDays` and not already reminded (dedupe key
  via the existing `lib/notify-state.mjs` pattern).
- `followup.mjs` (thin shell): load `job-state.json`, join with
  `applications/*.md` for `title`/`company`, compute due reminders, fire each via
  `osascript` ("Follow up: <company> — <title> (applied Nd ago)"), then record
  the reminder in notify-state so it doesn't repeat the same day.
- `com.eugene.jobs-followup.plist` — runs daily (~09:30). An `.example` variant
  is committed alongside, matching the repo's existing plist convention.

## Migration & graceful degradation

- On load the dashboard probes `GET /health`. If reachable, `/state` is the
  source of truth; any existing `localStorage.jobStatus` entries are POSTed up
  **once** (without overwriting newer server values), then cleared.
- If the server is unreachable (opened as a bare `file://` page, or server
  down), the dashboard **falls back to `localStorage`** and shows a small
  "offline — not saved to disk" badge. The page still works read/write locally;
  it re-syncs to the server next time it's opened via the server.

## Testing

Following the per-module convention:
- `test/job-state.test.mjs` — normalize (incl. legacy string upgrade), merge
  immutability, validate enum/date/note guards.
- `test/followup.test.mjs` — due-calculation across the threshold boundary,
  excludes non-applied and already-notified jobs.
- `test/freshness.test.mjs` — date-compare helper for `generated > lastVisit`
  (extract the comparison into a pure helper to keep it testable).
- Light server smoke test: start `state-server.mjs` on an ephemeral port, POST a
  patch, GET it back, assert the atomic write landed.

## Implementation phases (for the plan)

1. **Foundation** — `lib/job-state.mjs` + tests; `state-server.mjs` + smoke
   test; atomic-write helper; `Jobs.app`/`run.sh` launch-and-guard wiring.
2. **Tracking + Notes** — dashboard client talks to `/state`; reintroduce
   Applied + `appliedAt`; per-card notes; migration + offline fallback badge.
3. **Reminders** — `lib/followup.mjs` + tests; `followup.mjs`; launchd plist
   (+ `.example`).
4. **Find + Freshness** — search box, source chips, min-score presets; bake
   `data-generated`; `lastVisit` + 🆕 ribbon + counter. (Independent of the
   server except for `lastVisit`.)

## Out of scope (YAGNI)

Interview/Offer/Rejected stages, analytics charts, cross-device sync, auth,
browser-side editing of `.md` packages, language filter, exposing the server
beyond localhost.
